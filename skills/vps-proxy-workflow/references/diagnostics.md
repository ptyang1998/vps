# 性能、延迟与流量诊断

## 1. 拆分测量层次

先确认延迟来自客户端节点页、ICMP、TCP、首字节还是应用实际操作。比较设备时统一网络、节点、测试地址、协议和测量口径。

| 层次 | 能回答的问题 |
| --- | --- |
| 本机路由与接口 | 流量是否走预期物理接口，是否被其他隧道接管 |
| DNS 冷/热查询 | 首次解析与缓存的差异 |
| TCP 建连 | 到入口的连接时间与波动 |
| TLS 握手 | 证书验证与加密建连开销 |
| 代理首字节 | 代理建连、目标响应与路由的共同影响 |
| 持续下载 | 完成率、吞吐和超时，不能单独替代延迟测试 |
| 应用实际请求 | 用户感知与真实客户端路径 |

保留单次失败、超时与离群点，使用中位数等汇总时注明样本量。短样本出现一次 ICMP 超时不能推导长期丢包率；安装了虚拟网络软件也不能直接证明其导致问题。

## 2. 统一延迟是测量口径

Mihomo 的 `unified-delay` 计算 RTT，减少协议握手开销带来的测速差异。显示数字和整个探测请求的墙钟耗时可能不同，不能把开关后的数字下降当作实际链路同比提速。[Mihomo 统一延迟说明](https://wiki.metacubex.one/config/general/#统一延迟)

需要比较时，使用隔离核心和独立端口，保持同一测试地址与节点，只改变这一项。记录开关两种状态、完整请求耗时和显示结果，确认后再按用户意图应用到常用配置，测试进程及时退出。

## 3. BBR 对照测试

只有用户任务涉及服务端性能优化时才进行。先检查资源瓶颈、现有拥塞算法、内核支持和当前队列策略。目标内核已有 BBR 时，不为切换算法默认升级内核或重启服务器。

1. 记录原参数与持久文件，制定仅回退本次改动的恢复方式。
2. 在同一电脑、同一节点、同一下载源和相近时段做重复 A/B；需要排除时间趋势时可交替原算法与 BBR。
3. 同时记录下载完成率、吞吐、首字节与超时，控制测试流量。
4. 只有证据支持且属于授权范围时保存参数与持久配置，避免顺手改变 MTU、转发、防火墙或队列策略。
5. 如需刷新监听，评估目标服务重载/重启的影响，不随意重启其他服务。

下载更完整不代表网页延迟全面下降；当前生效不代表重启持久性已验证。记录“运行值”“已保存文件”“实际重启验收”三者的证据。

出现新错误或明显退化时恢复原参数；无新证据时停止重复试验。交付可重复测量的方法和局限，不承诺所有网络的收益。

## 4. 月流量与代理内容量

从当前套餐和面板读取配额、周期、重置时区、入站/出站计费方向及超额处理。公开文档使用抽象变量，不发布真实账单、套餐订单或服务器标识。

- 月配额记为 Q，Q 除以当月天数只是日均预算，不自动产生每天硬限制。
- 12Q 是年度累计预算，不能据此认定有跨月结转的年度池。
- 同一 VPS 的设备共享服务器配额，按设备增加配置不会增加套餐流量。
- 若商家同时计算入站和出站，代理搬运内容可能在服务器两侧分别计量；内容量约 Q/2 只是一种条件估算，还受方向、开销和其他服务影响。

面板的 GB/TB 换算、用量取整和更新时间也应核对。不能把条件估算当成套餐额度，或把旧客服说明当作当前确定计费规则。
