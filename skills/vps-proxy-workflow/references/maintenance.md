# 维护、恢复与交接

## 1. 保存能够恢复的变更记录

记录原状态、本次修改、有效运行结果和恢复入口；敏感配置与备份留在受限本地或用户指定私密渠道。备份完整性可以使用 SHA-256 核对，私钥和口令不写进普通操作日志。

恢复要匹配当前设备和对应变更：切回旧订阅、撤销新增域名规则、恢复 DNS、恢复服务参数是不同动作。已有其他编辑时按差异恢复，避免整份旧快照覆盖后续有效修改。

应用重新生成同名文件后，恢复工具应拒绝无条件覆盖。恢复前检查现有文件及备份，必要时先隔离冲突，核验后再恢复。

## 2. 按需的应用缓存维护

这项工作只有用户另外要求时执行，不作为部署或诊断代理的默认步骤。以 Claude 等桌面应用为例，区分缓存、日志、崩溃报告与登录、会话、项目、历史、设置和开发环境数据。

合适的流程为：正常退出应用 → 审查白名单 → 备份和校验 → 移入可恢复隔离 → 核对保护范围与恢复日志。拒绝路径越界、符号链接/junction、运行中变更和无效备份。

不要为网络排查轮换设备身份、重置登录、改变遥测或清空全部应用数据。大型受保护文件如果只比较大小和时间，应如实说明，没有完整哈希时不宣称内容逐字节一致。

缓存移入隔离且另存备份仍占磁盘，不把移动字节数宣称为净释放空间。清理结束后若任务要求网络恢复，使用实际应用验收；清理成功本身不能证明联网正常。

## 3. 按需的时间与位置设置

只有用户明确要求时间相关设置时才修改。先记录当前时区、自动时区、位置权限、自动校时和 NTP；每项独立判断，避免复制其他电脑的状态快照。

固定时区可以按需关闭自动时区，同时保留自动校时。时区改变不会改变公网出口，不能作为延迟或服务访问限制的通用解决方案。保持系统时间准确有助于正常 TLS 验证。

原设置已符合要求时记录“无需修改”。恢复使用本机快照，实际改过哪些项就恢复哪些项；不要推定关闭自动时区就必须改变位置权限或手动调钟。

## 4. 交接的四类状态

| 状态 | 应保存的证据 |
| --- | --- |
| 当前已验证 | 本设备、本次生效配置、测试时间与通过项 |
| 历史记录 | 来源和当时结果，明确没有证明当前状态 |
| 仅准备文件 | 语法检查范围，尚未实际导入/连接的设备 |
| 待后续验证 | 真实应用、移动端、续期、重启、UDP 或泄漏等具体缺口 |

建议交付两份材料：

- 通用方法文档：架构、实施顺序、验收方法、恢复原则和局限。
- 私密运行材料：实际配置、凭据、备份路径与恢复映射，使用独立私密渠道。

原部署成功不表示当前服务器、续期、算法或客户端仍处于同一状态；新设备只继承方法，不继承验收结论。

## 5. 公开发布检查

仅在用户已授权公开的范围发布。公开版从通用内容重新生成，不对私密工作目录执行整体添加或推送。

发布前检查完整文件集合，包括正文、文件名、元数据、链接、截图及可能推送的 Git 历史：

- 排除个人姓名、账户、邮箱、订单、设备名、本机用户名、用户绝对路径及真实服务器地址。
- 排除 UUID、SSH/TLS 私钥、密码、控制 API 密钥、订阅 token、节点 URI 与二维码。
- 删除可识别具体部署的套餐、账单、精确测量记录和私人来源链接；参数示例使用明确占位符。
- 检查扫描输出也不会回显匹配的秘密，模式扫描结合逐文件审查。
- 只发布明确列入清单的技能和方法文件，私密配置、原始日志及备份不进入发布集合。

写入后读取远端文件并比较内容或哈希，确认目标仓库与可见性符合用户当前要求。公开脱敏文档不会撤销源文件中仍存在的凭据，后者继续独立保管。
