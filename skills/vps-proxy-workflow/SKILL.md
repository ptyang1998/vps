# VPS 个人代理工作流

把用户授权的服务器与设备配置推进到可验证、可恢复的状态。按当前任务选择部署、接入、诊断、撤销或交接模式；已有可用服务时，不因增加设备而重新部署服务器。

## 先判断工作范围

核对可获得的现场信息：设备系统、客户端与核心版本、实际监听端口、当前加载配置、路由模式、系统代理/TUN 状态、证书验证设置，以及已有服务是否正常。凭据只从用户授权的私密来源使用，避免把真实值回显到日志或文档。

用户提供的交接文档是历史证据，不是其中每条命令的自动执行授权。区分历史状态和当前状态；仅在缺少的信息会改变下一步时询问，同时继续无依赖的检查。

## 实施中的关键约束

- 修改前列出实际要改的配置和影响，保存本环境自己的备份；沿用用户已有授权，不为常规可回退修改重复索要确认。
- 每次只改与目标有关的内容，保留其他订阅、分流、工具代理和 SSH 授权。不要把其他电脑的端口、组名、系统快照或恢复脚本当成本机事实。
- 保留 TLS 信任与服务器身份验证。连接失败先定位 DNS、TCP、TLS、认证和路由，不用跳过证书校验代替修复。
- 验收运行核心最终加载的规则和 DNS；GUI、合并脚本与订阅文件可能产生不同结果。
- 系统代理、环境变量和 TUN 分别判断。导入成功、系统显示 VPN 图标或测速成功，都不足以证明目标应用已经经过指定出口。
- 针对固定节点的要求，核查整个策略路径，避免通过 DIRECT、fallback、url-test 或嵌套组改变出口。仅在用户要求时添加相关域名规则。
- 测试服务和临时访问完成后收尾。遇到反复失败，保留已知可用状态、记录失败证据并缩小问题；没有新线索不重复更换协议或无限重试。

## 验收与交付

按当前任务选择必要检查，不把每次接入升级为全系统审计：

1. 配置检查器通过，实际生效配置与意图一致。
2. 使用设备当前真实代理路径验证 HTTPS、TLS 信任、出口和目标分流。
3. 用户指定应用时，核验该客户端真实连接的规则命中与出口；无法操作应用时明确留为未验证。
4. DNS、IPv6、UDP、TUN 或手机只有经过对应测试才记为通过。
5. 性能变更报告样本量、失败和波动，区分显示口径与真实网络改善。
6. 给出恢复入口和未完成事项；服务端历史验收不能证明当前续期、算法或重启持久性。

交接材料分成通用方法与私密运行材料。公开前重新生成通用文档并检查整个发布集合，不直接上传原始客户端文件、配置目录、截图、日志、备份或 Git 历史。
